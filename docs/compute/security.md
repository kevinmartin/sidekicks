# Compute security boundaries

This document describes the implemented local Docker design, not a production security certification. Docker Engine and its administrator are trusted. The host-side CLI can start code and access its guest through that Engine. Workload code and files are untrusted; container and host-kernel isolation are the outer boundary. A container is not a microVM, and its guest agent, browser UI and file path checks are not a sandbox against the code running inside the container.

The Docker backend requires a local Unix socket and creates only labelled, owned instances. It requests UID 1000, a read-only root filesystem, dropped capabilities, no-new-privileges, init, explicit CPU/memory/PID limits, bounded temporary filesystems and no host mounts or Docker socket. `network none` is the default. Explicit egress uses a Docker bridge: it can potentially reach the host, LAN and Internet, and is not an egress allowlist. Viewer ports are published only on host loopback. These controls depend on the selected Engine and host platform enforcing them; no isolation-escape test or hostile-host guarantee is claimed.

The private guest agent requires an instance bearer token and rejects browser Origins. It offers command execution by design to the authorized compute client; a compromised workload running as the same guest user must not be assumed unable to access its own agent or token. Workspace file operations use a confined root and bounded request/output sizes, but shell commands can access anything permitted inside the guest. Workspaces are ephemeral, not durable storage.

The local desktop viewer uses a short-lived one-time ticket, a cookie, exact loopback Host/Origin checks and lease epochs. It is intended for a trusted local machine, not as Internet-facing authentication or encrypted transport. RFB and Neko SDK transport are receive-only for input; supported input passes through the lease-gated checked X11 driver. Uncertain X11 I/O fails closed until restart. The gate cannot retract application events already delivered, and deliberately detached command descendants may require destruction of the whole container. See [Neko's upstream input decision](../../internal/compute/neko/UPSTREAM-SAFETY.md).

Release gaps remain: the current Docker image references can identify mutable local tags; image signatures, provenance attestation and a verified deployment/promotion policy are not implemented. Debian repositories are not snapshot-pinned. The clean Neko build pins the supported Go 1.27.3 toolchain; the pin must be maintained as Go releases age out under the [Go release policy](https://go.dev/doc/devel/release#policy). Advisory scans are time-bound and are not a substitute for a complete image scan or an independent security assessment. A clean `make verify` with stable neighboring resources, multi-platform runtime tests, security review and an explicit supported-operating-environment policy are required before calling the compute layer production-ready. See [status](status.md) for the actual current evidence and failures.
