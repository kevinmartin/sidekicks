# Local compute development

Make is the supported entry point. Run `make setup` once to install the exact npm lockfile plus Staticcheck v0.8.2 and govulncheck v1.9.0 into repository-local `.run/` paths. Installation requires authorized network access; check targets do not install tools or silently substitute versions. Go's installed toolchain must satisfy go.mod; `GOTOOLCHAIN=local` prevents an implicit toolchain download. `STATICCHECK_CACHE`, `GOCACHE` and `GOPATH` stay under `.run/`.

`make check` runs formatting for owned Go (including `web`), pinned-web Prettier and e2e JavaScript syntax, Go vet, the pinned Staticcheck binary, race-enabled unit/component tests, statement coverage policy and static production-package compilation for Linux arm64 plus amd64. Compile success does not mean either architecture has run successfully. Networked httptest/WebSocket tests need permission to bind task-local loopback ports; denial is a failed/uncompleted check, never a skipped PASS.

The overall coverage floor is80% of **all** instrumented statements in `internal`, `cmd` and `web`, with no low-coverage command wiring removed from the denominator. Additional required floors are90% for ownership control and Docker runtime,85% for guest and browser, and80% for Neko. Missing critical packages fail. Current command/orchestration coverage may be below this policy; do not lower it silently or call a failed coverage gate a completed check. `make coverage` prints detailed current function coverage. Integration/e2e execution is separate evidence, not automatically included in the unit coverage file.

The historical POC is preserved on `reference/poc`; ignored disks and evidence remain local. Cached dependencies and upstream third-party code are outside owned formatting/lint. Docker-independent integration guards run during `make check` with live integration explicitly disabled. Actual Docker and Linux-in-guest tests require their explicit integration/e2e windows; ordinary checks do not imply those tests ran.

`make build IMAGE_ARCH=arm64` (or amd64) builds the host CLI and static Linux agent for the selected image platform. `make images` additionally builds the pinned SDK web bundle and invokes `build-images.sh`: all four named targets of the clean shared Dockerfile are built as `sidekicks-compute/<adapter>:clean` and `:dev`. No old local POC image is a prerequisite. Only these new compute tags are updated; containers, POC tags, VM state and evidence are not deleted. Build APT/software downloads are explicit in this target, not part of offline checks.

For verification without replacing existing tags, run `make images-candidate IMAGE_ARCH=arm64` (or `amd64`). It builds the four targets under a fresh, collision-checked `verify-<random-id>` tag, inspects each resulting immutable image ID and platform, and writes a `built-not-verified` manifest, per-target build logs and completed identities under `artifacts/compute/candidate-build/<random-id>/`. An interrupted or failed run retains its partial tags and failure evidence; it is not promoted or automatically deleted. Existing `:clean` and `:dev` tags are not modified. An already-present tag or evidence directory makes that run fail closed. A caller may provide `SIDEKICKS_CANDIDATE_RUN_ID` as exactly 32 lowercase hexadecimal characters; it is subject to the same collision checks. Docker does not offer an atomic tag reservation here, so do not run concurrent builders with the same run ID.

The candidate manifest binds the observed Git revision, dirty state, tracked changes and untracked-file fingerprint (including ignored files in the relevant image-input trees), and exact generated agent/web-bundle hashes before and after the builds. The agent's Go build metadata must match the selected Linux architecture and Git state. These checks detect ordinary source drift, but are not a signed provenance attestation and cannot rule out a transient change-and-revert during a build. APT is not snapshot-pinned, and Docker may fetch an absent pinned base; review the recorded build logs and perform independent vulnerability and functional verification.

To test the shell and headless browser candidates, supply their exact manifest IDs as `SIDEKICKS_TEST_SHELL_IMAGE=sha256:...` and `SIDEKICKS_TEST_BROWSER_IMAGE=sha256:...` to `make integration-candidate`. Mutable tags and missing IDs are rejected, and the separate app lifecycle harness is explicitly disabled. This target runs only those two owned-container tests; it does not audit unrelated containers by itself and does not replace desktop E2E, isolated app/media checks, release scanning or independent acceptance.

`SIDEKICKS_DOCKER_SOCKET` selects an absolute local Unix socket (default Docker Desktop's user socket on Darwin, `/var/run/docker.sock` on Linux). Build scripts pass that socket explicitly rather than inheriting an arbitrary Docker context or TCP host. `SIDEKICKS_IMAGE_ARCH` is passed by Make from `IMAGE_ARCH`; only arm64/amd64 are accepted. Make must rebuild the static agent when changing platform.

`make verify` runs `make check`, builds a uniquely tagged four-image candidate set, then passes the resulting immutable image IDs to actual shell/browser integration, both desktop application lifecycle tests, and both desktop E2E tests, including synthetic Neko audio. It does not retag or promote existing images. Verification stops on a failure, checks the source fingerprint between steps and writes incremental results under the candidate evidence directory. The app lifecycle tests use test-only derivatives of the selected desktop images; desktop E2E uses the unmodified images. It requires Docker permission, locked web dependencies and installed Google Chrome; image builds also require access to their upstream dependencies. Missing prerequisites are failures. Source fingerprints detect ordinary drift but are not signed attestations. `make vuln` and `make release-verify` remain separate because the advisory database is a network-dependent, time-varying input.

`make clean` removes only the two named compute binary outputs. It does not prune Docker, erase reports or remove POC files. No clean target runs automatically.

Release metadata/advisory tooling is described in [security/README.md](security/README.md). `make check` deterministically tests/lints that tool and gates its separately reported coverage; `make release-verify` is the explicit network-dependent, local-image release check. It never silently substitutes for the integration/e2e matrix or a signed provenance attestation.
