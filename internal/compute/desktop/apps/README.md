# Fixed guest desktop applications

`Launcher` owns Browser, Terminal and Files launch-or-restore behavior. It runs inside a guest/container as the desktop user. `NewX11` accepts only numeric local Unix X11 displays and uses XGB; it does not run shell commands or touch the host display. Only `_NET_CLIENT_LIST` normal clients with the managed class/role and useful geometry are eligible. Activation sends `_NET_ACTIVE_WINDOW`, preserving the same client, tabs and geometry.

One in-process lock and one guest filesystem advisory lock per application prevent queued duplicate launches. A pending PID marker covers helper/request cancellation and separate launcher processes; Linux markers include the process start identity so PID reuse does not indefinitely suppress a new launch. If marker persistence fails after a child starts, the advisory lock is retained until its window appears or its exit and delegation grace period complete. Pending successful D-Bus delegates receive a 15-second grace period; an app still alive without a normal client stays pending instead of spawning copies. Unknown marker state fails closed. This is operational coordination among the owned launch paths, not protection against another guest process deliberately launching apps.

Children use fixed absolute executables and argv, a fixed locale/PATH, explicit guest HOME and only DISPLAY/session-bus environment passthrough. Sidekicks tokens, proxy credentials, preload variables and other parent environment are absent. Request cancellation never kills an already started app; its `Wait` is reaped separately, and container lifecycle remains responsible for terminating guest processes.

Chromium receives CSD, Home and New Tab settings in its dedicated managed profile. Existing restored windows never have their profile edited or tabs navigated. Firefox receives its managed profile/class/Home; the image's validated Firefox enterprise policy and AutoConfig remain responsible for New Tab behavior. The common terminal launch uses `--role=SidekicksTerminal`, supported by both tested Xfce terminal versions; newer-only `--class` is not required. Files uses ordinary Thunar, never desktop ownership.

`Handler` accepts POST JSON `{ "app": "browser" | "terminal" | "files" }` only. It is plumbing, not authentication: the root agent must wrap it with the internal-Home authority and active ownership gate. `State` only proves a current managed-client query succeeds, including after apps close; session/compositor readiness is a separate lifecycle check. Menu curation is not a security boundary.

Unit tests inject EWMH windows and process startup, cover concurrent/canceled launches, same-client restore, close/reopen, environment/argv, profile persistence and HTTP bounds. Real X11/WM behavior requires isolated guest integration; no live POC or user's desktop was used by these unit tests. `ChromiumNoSandbox` defaults false; any compatibility exception must be explicit and documented by the image owner.

The opt-in `TestRealGuestApps` requires a fresh disposable Linux guest at UID1000, `SIDEKICKS_APPS_TEST_DISPLAY`, and `SIDEKICKS_APPS_TEST_HOME`. It refuses an already occupied managed-app display. `SIDEKICKS_APPS_TEST_HOME_URL` defaults to `http://127.0.0.1:8080/home`; the actual managed browser window title must contain `SIDEKICKS_APPS_TEST_TITLE` (default `Sidekicks`). `SIDEKICKS_APPS_TEST_BROWSER=firefox` selects Firefox explicitly; empty or `chromium` retains the original Chromium default, and unknown values fail before connecting to X11. The same strict assertions apply to either browser. It tests real XGB/EWMH launch, two iconify/restore rounds with exact client/PID/geometry, and each app's WM_DELETE_WINDOW/500ms closed interval/explicit reopen. It does not test New Tab or physical input. Compile with `go test -c -cover` for the guest's Linux architecture and run the complete test binary with `-test.coverprofile=/workspace/apps.cover` to combine injected and actual-X11 coverage. Running that test is a separate explicit guest-integration action; compiling it is not evidence of a pass.

Initial workload readiness must follow `Launch(Browser)` with `WaitFor(ctx, Browser)`. A `launching` response is not a ready browser: `WaitFor` requires a normal managed client whose current X11 map state is viewable, and is bounded by `LaunchTimeout` even with a background context. It reports a known child failure or an explicit timeout without retry-spawning applications. Use this once as a startup barrier; do not continuously require the browser window for health, because intentional close/minimize must leave the desktop session ready.


A separate immutable-image coordinator is documented in [the isolated app lifecycle harness](../../../../test/integration/apps-lifecycle.md). It never accepts an existing container, requires an exact candidate image and current static test binary, and keeps the test desktop unpublished/network-none. A compiled harness or offline guard PASS is not a live Firefox lifecycle PASS.
